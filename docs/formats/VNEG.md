# VNEG 스크립트(.scn) 포맷

Studio Miris VN 엔진의 시나리오 스크립트. 확장자 `.scn`, AXRe 아카이브(`scenario.axr` + 패치 증분 `ax2`, `ax3`, …) 안에 있다. 정수는 **big-endian**.

## 전체 레이아웃
```
[헤더 8B] [심볼 테이블 N개] [점프/라벨 테이블] [flow 코드]
                            └ 여기부터를 "flow_start"라 부른다
```

## 1. 헤더 (8바이트)
```
56 4e 45 47              "VNEG" 매직
<unknown:2 BE>           시나리오 씬은 보통 0
<defcount:2 BE>          심볼 **정의** 수 (예: 00 be = 190)
```

## 2. 심볼 테이블 (defcount개 정의)
각 정의는 명령층 문법 `<op> <slots:2 BE> <argc> <args>` 다. **op = 객체 타입 id**
(아래 §5 타입표). `slots`는 이 정의가 차지하는 연속 런타임 심볼 슬롯 수다.
인자 태그: `01`+int32BE(정수) / `00`+cstr\0(문자열).

- 보통 `slots=1`; 이때 여러 인자는 layer/button/textwindow 한 객체의 생성자 인자다.
- `slots>1`인 int/string 배열은 `argc=slots`이고 initializer 하나가 런타임 슬롯
  하나에 대응한다. 미초기화 배열은 `argc=0`이다.
- 따라서 flow의 심볼 인덱스는 정의 순번이 아니라 앞 정의들의 `slots` 합으로 정한다.
  `defcount`와 런타임 슬롯 수가 다를 수 있다.

exe 근거(神無ノ鳥): `0x414340`이 `[6:8]`의 defcount만큼 정의를 읽고, `0x405AD0`이
slots를 저장한다. `0x4143B2`가 slots번 런타임 심볼을 만들며 `0x4127B7`(int) /
`0x41288E`(string)가 initializer `i`를 슬롯 `base+i`에 넣는다.

- `op=03`(string): 리소스명·인물명·대사옵션·**분기 씬이름** 등
- `op=02`(int): 좌표·시간·볼륨 등

심볼은 flow에서 **런타임 슬롯 인덱스**로 참조된다. 2바이트 BE 값은
`0x1000 + index`다. 예 `10 9e`=심볼158, `11 00`=심볼256,
`11 db`=심볼475. 인덱스 참조라 씬이 밀려도 안전하다.

예(0506_01):
```
#155 string "m_a_00"          BGM
#158 string "movie/opening.dmj" 무비
#185 string "「自殺の手伝いは…」" 선택지 옵션1
#186 string "「気が乗らなかったから」" 선택지 옵션2
#187 string "0506_01a"         선택 분기 씬
#188 string "0506_01b"         선택 분기 씬
```

## 3. 점프/라벨 테이블 (flow_start)
심볼 테이블 직후, flow의 맨 앞에 위치. **선택지 분기·무비 시작·BGM 전환 등 모든 점프의 목적지 테이블**.
```
<N:u16 BE>  00 00 00 00 00 00      헤더 (N=엔트리 수)
entry[0] = 00 3b 00 00              0x3b = 제어코드/상수 (모든 씬 동일 — 오프셋 아님, 건드리지 말 것)
entry[1..N-1] = <offset:2 BE> 00 00 flow상대 절대오프셋
```
- **점프 타겟 = flow_start + offset** (씬 시작이 아니라 flow_start 기준!).
- exe 경로: 분기/대기 opcode → `0x408be0`(arg1=0) → `0x408ce7` → `0x4147a0`가 `base + labelTable[idx]` 계산 후 커서=0. base=flow데이터 시작.

예(0506_01, flow_start=0x9bd):
| entry | offset | → 타겟 | 의미 |
|---|---|---|---|
| [0] | 0x3b | (제어코드) | 상수 |
| [1] | 0x383d | 0x41fa | BGM(심볼155) 전환 |
| [2] | 0x385d | 0x421a | **무비 커맨드**(`02 10 9e`) |
| [3] | 0x4340 | 0x4cfd | 선택지 분기 로직 |
| [4][5] | 0x4356 | 0x4d13 | 분기 값 비교 |
| [6] | 0x4360 | 0x4d1d | **0506_01a 분기**(심볼187) |

### ⚠️ 한글 패치 버그와 수정
한글 패처가 텍스트만 치환하고 **이 오프셋들을 갱신 안 함** → KR 씬은 더 길어 위치가 밀렸는데 오프셋은 JP값(스테일) → 점프 시 엉뚱한 위치 → **hang/크래시**(무비 안 나옴·선택지 선택 시 죽음·전체가 시작조차 안 함).

**수정**: 주입기가 알고 있는 치환 스팬으로 JP 위치를 KR 위치에 직접 대응시켜,
```
O_kr = jp2kr(fj + O_jp) - fk      # fj/fk = JP/KR flow_start
```
로 재계산한다. 치환 스팬이 없는 단독 재매핑은 difflib을 폴백으로 쓴다.
entry[0](0x3b)은 flow상대로도 0x3b 유지되므로 그대로다. 검증:
`jp[fj+O_jp:+6] == kr[fk+O_kr:+6]`이면 정확하다. 구현:
`miris.vneg.relocate_jumptable` (CLI `ujyu scn relocate`).

재매핑할 때 `O_jp`는 반드시 **JP 원본 테이블**에서 읽는다. KR 테이블은 이미 한 번
재매핑됐을 수 있다. KR 값을 다시 원본처럼 쓰면 실행할 때마다 이동량이 누적된다.
현 구현은 JP 기준이라 멱등이며, 같은 빌드에 재실행해도 바이트가 변하지 않는다.

#### 타겟 종류 두 가지 (재매핑 규칙이 다르다)
1. **명령 경계 타겟** (대다수) — 분기·GOTO 목적지. 원본 바이트가 그대로 남으므로
   `새 오프셋 = 원본 + 앞선 길이변화 누적` 으로 **정확히** 계산된다.
2. **텍스트 내부 타겟** (神無ノ鳥 실측 1,215개 중 130개) — 나레이션 텍스트 런
   **안쪽**을 가리킨다. 전부 문장 **끝에서 1~15바이트** 이내이고, 바로 뒤에
   `04 7f 00 74`(END)가 온다. 즉 텍스트 시작이 아니라 **뒤따르는 END 에 붙은 앵커**다.
   (예: `0510_04a.scn` `IF≠0→ L1`, L1=텍스트 마지막 문자 「。」의 둘째 바이트.)
   → 재매핑은 **끝에서의 거리를 보존**해야 한다: `새끝 - (원끝 - P)`.
   시작 기준으로 옮기면 문장 길이가 바뀐 만큼 어긋난다.

주입기가 치환 목록(오프셋·원길이·새길이)을 넘기면 두 종류 모두 계산으로 처리되어
difflib 정렬이 필요 없다 (`relocate_jumptable(kr, jp, edits)`).

## 4. flow 코드 (마이크로 바이트코드)
`0x408E00` 리더가 바이트를 분류한다:

| 바이트 | 처리 |
|---|---|
| `0x00`–`0x2F` | **opcode** — 점프테이블 `0x409B54`(**48엔트리**)로 디스패치 |
| `0x30`–`0x7F` | 커맨드 (일부는 뒤 2바이트를 오퍼랜드로 삼킴) |
| `0x80`–`0xFF` | **표시 텍스트** — 인라인 2바이트 조립(SJIS/CP949), opcode 아님 |

- 리더 커서 `[esi+0x48]` = **베이스 `[esi+0x44]` 상대** (스트림 위치독립, 순차 읽기). continue=`0x409B49`.
- 심볼 참조: `0x1000 + idx`인 2바이트 BE 워드. `#0`은 `10 00`, `#256`은
  `11 00`이다. `[sym]` = 그 opcode의 워드 오퍼랜드가 런타임 심볼 인덱스라는 뜻.

### 4-1. 전체 opcode 표 (0x00–0x2F)
컬럼: **OP**=opcode 바이트 · **IMM**=즉치워드(있을 때만; `0b`/`0f`는 동작 선택 마커 w1, `0d`는 서브코드 바이트) · **이름**=(OP, IMM) 조합의 구체 동작 · **operand**=나머지 오퍼랜드.
- **즉치워드**(IMM) = 스트림에 리터럴로 박힌 값. 심볼 인덱스가 아니라 그 자리서 읽는 상수라, **같은 OP라도 IMM 값에 따라 이름이 갈린다**(예 `0b`).
- operand 약어: `idx`=라벨 인덱스(2B) · `[sym]`=심볼참조
  `0x1000+idx`(2B) · `int32`=4B 리터럴 · `list`=count+워드 ·
  `특수`=고정 시퀀스 · `—`=없음.
- 상태 아이콘 ✅확정 · ◐부분. 이름이 부분 해석인 opcode도 피연산자 길이는 exe
  핸들러로 확정했다(§4-5).

| OP | IMM | 이름 | operand |
|---|---|---|---|
| `00` | — | HALT_THREAD ✅ | — |

| `02` | — | CALL_METHOD_INDIRECT ✅ | `01`과 동일, 참조를 한 번 더 해석 |

| `05`–`09` | — | RESERVED_NOP ✅ | — |

`0x00`–`0x2f`의 핸들러와 피연산자 소비량은 전부 확인했다. 남은 의미 분석
대상은 `0b`/`0d`/`0e` 등 일부 서브타입과 객체 타입별 `0x30`–`0x7f`
메서드다. (`0x80`+는 표시 텍스트이며 opcode가 아니다.)

**exe 핸들러 예**: 00@`408e45` · 02@`408e54` · 03@`408f3e` ·
10@`40911a` · 17@`4092aa` · 1a@`409352` · 20@`409553` ·
21@`409597` · 2a@`409868` · 2f@`4098a9`.
⚠️ `10`(GOTO opcode)과 심볼참조 워드의 첫 바이트 `10`은 순차 파싱으로
구분한다(§4-4).

### 4-2. 커맨드(0x30–0x7F) · 텍스트(0x80+)
- `0x30`–`0x4f`는 `u16 객체참조` 뒤 객체 메서드 `op-0x30`을 호출한다.
  따라서 `31 00 00 <int32:4 BE>`는 내장 객체 `#0`의 m01 패턴이며,
  디스어셈블러가 읽기 쉽게 **IMM**으로 표시하는 파생 표기다.
- `0x50`–`0x5f`는 직전 객체 메서드, `0x60`–`0x7f`는 전역 호출이다.
  개별 메서드 의미는 타입별 vtable 분석이 더 필요하다.
- `0x80`–`0xFF` = **표시 텍스트**. 텍스트 블록 안에서만 진짜 텍스트(아래).

#### 텍스트 블록 (표시 텍스트 판별)
표시 텍스트는 **블록** 단위로 나온다 (`miris.vneg.extract` 가 이 규칙으로 추출):
- **블록 오픈/전환**: `<symref:u16>`에서 **symval[sym]이 int
  0(나레이션)/1(대사)** — 모드 심볼 인덱스는 씬마다 다르다(`10 04`/`10 02`는
  한 예이며 `11 xx`도 유효). `0d 34 00`(네임윈도우 닫기)
  뒤는 여는 괄호 블록(`「z`).
- **블록 유지(인라인 통과)**: `00`/`01`(글루)·printable 1바이트 커맨드(`z` `%` `*` 등)·
  `0d XX`(네임윈도우류)·`10 XX`/`11 XX`(심볼 참조)·
  `04|12|13|14|15 XX 00`(클릭대기·페이지류, `04 7f 00 74`=END 제외)·`0x80`(비-리드 글리치).
- **블록 종료**: 그 외 제어 op(분기/점프 등), END, 그리고 `%`(0x25)로 끝난 런(대사 종료).
- **런(레코드)**: 블록 안 연속 2바이트 SJIS(+인라인 printable·반각가나). 2바이트 리드로
  시작해야 한다 — 리드가 아닌 선행 1바이트는 직전 op의 operand다.
- 화자: `0d 33 01 <symref:u16>`(SPEAKER op)의 심볼이 이후 대사·괄호
  블록의 화자.
  (보이스 프레임 `01 10 <voice>` 기반 추정은 무음 대사에서 틀린다 — 실측 365건.)
  `0x11xx` 화자참조도 실제 8개 아카이브 엔트리에서 107명령 확인했다. 유효본
  기준 6개 씬의 추출 레코드 183건이 이전의 낡은 화자 상태에서 정확한 화자로
  교정됐다.

#### ⚠️ 1바이트 vs 2바이트 (번역 대상 판별)
`.scn`에서 **화면 표시 텍스트 = 텍스트 블록 안 2바이트 SJIS 런만**이다. 1바이트 문자는 대부분 **제어코드/오프코드 operand**이며 표시되지 않는다.
- `z` (0x7A): 「 / （ 뒤의 **대사·독백 마커**(control, 미표시).
- `%` (0x25): `」%`의 **대사 종료(클릭 대기)** 코드(미표시).
- 단독 반각가나(ｨ ｩ ｪ …, 0xA1–0xDF): `<01><10>` 오프코드의 **operand(음성/리소스 ID)**. 순차 증가, 텍스트 아님.
- `<00>–<1F>` 바이트 및 프레이밍(`03 00 01 01 00` 등): 오프코드/레코드 경계.
- 블록 밖에서 SJIS로 읽히는 2바이트(`钁` 등)는 flow 오퍼랜드 오탐 — 추출하지 않는다.
- 런에 포함된 1바이트 커맨드(`z` `%` `\n` 등)는 주입 시 원본 바이트 그대로 보존한다
  (`inject_text.encode_piece`).

#### 데이터 화면 (.scn인데 스크립트가 아닌 것)
`music.scn`·`scene.scn`·`load.scn` 등 일부 화면은 심볼 테이블에 문자열이 거의 없고
flow가 **널종료 문자열 배열**(BGM id·곡 해설·씬 제목 등)이다. `extract`는 텍스트
블록이 전혀 없는 파일에서 00 경계 cp932 완전 디코드 문자열을 `cstr` 레코드로 뽑는다.

### 4-3. 선택지 if/else 예 (0506_01, `if sel goto 0506_01a else 0506_01b`)
```
L3:                        선택 분기 로직
  IMM 1                    케이스값 (op31)
  IF≠0→ L4                 op17: 불일치면 다음 케이스로
  GOTO 0506_01a            op0b(001e): 일치 → 씬a
L6:
  IMM 2
  IF≠0→ L5
  GOTO 0506_01b            → 씬b
```
⚠️ 라벨 타겟은 **명령 시작점**이다. 단 select 케이스 데이터를 가리키는 엔트리는 op 중간처럼 보일 수 있음.

### 4-4. 심볼참조 판별 (오검출 주의)
opcode를 **순차 파싱**하며 `[sym]` op의 워드 오퍼랜드 `v`가
`(v & 0xf000) == 0x1000`이면 `v & 0x0fff`가 런타임 심볼 인덱스다.
즉 `10 ff`는 #255, `11 00`은 #256이다. 실제 씬에서 #256–#476 참조
2,703건을 확인했다. 파싱 없이 `10 XX`를 무조건 심볼로 보면 opcode
`0x10`(GOTO) 등과 혼동해 오검출한다. `miris.vneg`의 구조화 flow 명령 검출은
오탐 방지를 위해 확정 5개(02/03/07/08/0c)만 화이트리스트로 쓰고, raw flow의
심볼 참조 주석은 범위 검증을 곁들인 휴리스틱으로 표기한다. 심볼 테이블 자체는
전체 23타입을 식별한다.

### 4-5. flow 명령 인코딩 — 인터프리터 구조 (실측, authoritative)

디스패처 `0x408E00` 를 그대로 읽어 확정했다. 구현: `miris.vneg.walk()`.

```
바이트 하나를 읽어 op 로 쓴다.
  op < 0x30    점프테이블 0x409B54 (48엔트리). 피연산자는 아래 표.
  0x30..0x4F   u16 객체참조            -> 객체.메서드(op-0x30) ()
  0x50..0x5F   u8 argc + argc×u16      -> 직전 객체.메서드(op-0x50)(인자)
  0x60..0x7F   u8 argc + argc×u16      -> 전역 호출
  0x80..0xFF   +1바이트                -> 2바이트 표시 문자 (shl 8 | 다음바이트)
```

- **정수 피연산자는 전부 빅엔디안**이다 (`mov dh,[p]; mov dl,[p+1]`).
- **심볼 참조 = `(u16 & 0xf000) == 0x1000`**. 인덱스는 하위 12비트이며
  실제 런타임 심볼 수보다 작아야 한다.
- `op 0x01/0x02` = 객체 명령: `u16 객체참조, u8 메서드, u8 argc, argc×u16`.
  0x02 는 참조를 한 번 더 해석한다(`0x4089B0` + vtable).

`op < 0x30` 피연산자 길이 (핸들러가 스트림을 전진시킨 바이트 수):

| op | 길이 | op | 길이 |
|---|---|---|---|
| `00` `04` `05`–`09` `1f` `2a`–`2f` | 0 | `0a` | u16 + u32 |
| `01` `02` | 가변(위 참조) | `0b` `0c` `0d` | u16 + u16 |
| `03` | u16 + u8 | `0e`–`1b` `24` `25` | u16 |
| `1c` `1d` `1e` | u8 count + count×u16 | `20` `21` | u32 |
| `22` `23` | u8 | `26` `28` | u32 + u16 |
| `27` `29` | u8 + u16 | | |

⚠ **메서드가 스트림에서 더 읽을 수 있다.** `0x30..0x4F` 핸들러는 객체를 찾은 뒤
vtable(`[eax+0x2c]`)로 넘기고, 그 구현이 즉치를 더 소비한다. 실측: `m00`(대입)·
`m01`(더하기)는 int32 를 하나 더 먹는다 — 대상이 심볼이든(`30 10 0c 00 00 00 01`
= `#12 += 1`) 내장 객체든(`31 00 29 00 00 00 01`) 같다.

`walk()`는 확인한 핸들러와 같은 바이트 수를 소비한다. 다만 HALT·분기 뒤의
도달 불가능 데이터 때문에 “파일 끝까지 선형 완주” 자체는 정확도 지표가 아니다.
대신 원본 4개 아카이브의 569개 엔트리 전부에서 심볼/점프테이블 경계와 알려진
호출을 검증했고, 파싱·디어셈블 예외가 없음을 확인했다. 다른 객체 메서드가 즉치를
더 소비하는지는 타입별 vtable 분석으로 계속 보강한다.

> **씬 종결 트레일러(실측).** 다수 story 씬은 끝에 13바이트
> `1e 10 <sym> 01 00 26 01 01 00 02 11 00 1e`(가운데 sym만 다름)가 붙어 있고,
> **어떤 라벨/점프도 이 영역을 가리키지 않는다**(0506_01: 라벨 최대 `0x4d1d` < 꼬리
> `0x4d32`). 실행되지 않는 죽은 데이터다. 여기 `1e`를 op1e(count+u16)로 만나면
> count=16으로 32바이트를 요구해 walk 가 멈추는데, 이는 정상이다 — 실제 코드는
> 정확히 파싱된 뒤다. (op1e/03/27 을 짧게 잡으면 이 꼬리를 우연히 완주하지만
> 실행 안 되는 바이트를 코드로 오독하는 것이라 지표로서 무의미하다.)

> `0x50..0x7F` 는 **객체참조를 갖지 않는다** — 핸들러가 바이트 하나를 먼저 읽어
> argc 로 쓴다(`0x409906`/`0x4099a1`/`0x409a3d` 모두 동일). 대상은 직전에 해석된
> 객체다. 여기를 u16 객체참조로 잘못 읽으면 story 씬 대부분이 어긋난다.

## 5. 심볼 op = 객체 타입 id
exe 타입 레지스트리 va `0x475818` 실측(2026-07-27, authoritative).
문법: `<op> <slots:u16 BE> <argc>` + 타입인자(`01`+int32BE /
`00`+cstr). 헤더의 정의 수와 런타임 심볼 수는 다를 수 있다.

| op | 타입 | | op | 타입 |
|---|---|---|---|---|
| `00` | object | | `0c` | **button** |
| `01` | bool | | `0d` | threadinfo |
| `02` | int | | `0e` | stringflag |
| `03` | string | | `0f` | thread |
| `04` | flag | | `10` | scenario |
| `05` | register | | `11` | engine |
| `06` | event | | `12` | display |
| `07` | **layer** | | `13` | soundsystem |
| `08` | **textwindow** | | `14` | timer |
| `09` | textwindow2 | | `15` | eventsystem |
| `0a` | soundtrack | | `16` | **scroll** |
| `0b` | file | | | |

(이전 `07`=DRAW / `08`=RECT / `0c`=SCREEN 은 오판이었다.)
`scroll`은 실제 `ex26.scn` 1개와 `rolltest2.scn` 3개 정의에서 확인했다.
생성자 arg0..3은 x,y,w,h, arg4는 bool, arg5는 int다.

## 도구
- `ujyu scn`(= `miris.vneg`) — VNEG 디스어셈블러(심볼·점프테이블·flow
  hex + 인라인 텍스트) + 구조적 텍스트 추출(`extract`, §4-2 텍스트 블록 규칙) +
  점프테이블 재매핑(`relocate`). 여러 레이어를 한 번에 디어셈블하면
  `scenario_axr`/`scenario_ax2`/`scenario_ax3`/`scenario_ax4`로 분리해 동명
  파일을 덮어쓰지 않는다(506+46+16+1=569).
- 텍스트 파이프라인: `scn.py extract`(원본→strings.json v2) → 번역 →
  `inject_text.py build`(주입+재매핑). DB 호환을 위해 추출기의 `sym:<id>`는
  레거시 **정의 순서**를 유지한다. 디어셈블의 `#id`와 flow 심볼참조는
  **런타임 슬롯 인덱스**다. `flow:<디코드순번>`과 원본 바이트 스팬도 함께 쓴다.

  그대로였고 화자 메타데이터 183건만 교정됐다.
- 새 구조를 파악할 때마다 이 표의 부분 해석과 타입별 메서드를 채우고
  `miris.vneg`에 반영한다.

## 6. UI 씬의 좌표 구조 (메뉴·세이브·설정)

명시 치수로 그리는 화면(RESOLUTION.md §4)의 좌표는 **세 군데**에 나뉘어 있다.
해상도 N× 확대는 이 셋을 모두 손봐야 한다 — 하나라도 빠지면 버튼만 움직이고
글자는 제자리에 남거나 열이 겹친다(실측). 도구: `ujyu/scn_dims.py`.

### 6-1. 객체 심볼 정의의 앞 인자

심볼 문법은 `<op> <슬롯수:2 BE> <argc> <args>` 다. 슬롯수는 보통 1 이지만
int/string 배열은 initializer마다 **서로 다른 연속 심볼 인덱스**를 차지한다(§2).
앞쪽 인자가 치수다:

| 타입 | 인자 |
|---|---|
| `layer`(07) / `button`(0c) / `scroll`(16) | x, y, w, h, (id …) |
| `textwindow`(08) | x, y, w, h, 여백 L, T, R, B, (id …) |

예 `save.scn` #0 = textwindow(0, 0, 640, 480, 0,0,0,0, 9) — 목록 전체를 덮는 창.

### 6-2. 객체 메서드 호출

```
01 10 <객체심볼> <메서드> <인자수> (10 <심볼>)*
```

실측 확정 (神無ノ鳥 save/load/config):

| 호출 | 인자 |
|---|---|
| `button.m02` | x, y, w, h, id, 이미지off, 이미지on [, mode, 이미지select] |
| `textwindow.m10` | x, y, w, h, 여백 L, T, R, B |
| `textwindow.m41` | 텍스트 x, y, 문자열 [, flag] (x=-1 은 자동) |
| `textwindow.m18` | 선택지 버튼 치수 2개, 라벨, id, id |
| `textwindow.m07` | 글꼴 크기 |
| `textwindow.m44` | 창틀 이미지 6개(h, v, lt, rt, rb, lb) |
| `textwindow.m45` | 색, 알파 |
| `layer.m02` | 이미지, 레이어 인덱스 |

`scn_dims.py`는 flow 순차 파서를 우선 사용한다. 아직 피연산자가 미확정인 scratch
메서드 뒤에서 경계가 잠깐 어긋나는 경우에는 실제 객체 타입·알려진 메서드·전 인자의
심볼 타입이 모두 맞는 명시 호출만 보수적으로 합친다. 좌표 자리에 int가 아닌 심볼이
오면 그 호출은 건드리지 않는다. `config.scn`도 이 검증을 거쳐 자동 스케일된다(§6-5).

### 6-3. 변수 즉치

목록의 행 좌표처럼 런타임에 넣는 값은 flow 의 즉치에 있다:

```
0a 10 <심볼> <int32 BE>    변수 = 값
30 10 <심볼> <int32 BE>    변수 += 값     (열 이동. save.scn 은 +155 로 날짜 열)
```

그 변수가 좌표 자리(`m41` 등)에만 쓰이면 즉치도 좌표다. `load.scn` 처럼 같은
파일에서 다른 변수가 **슬롯 번호 카운터**로 쓰이기도 하므로, 쓰임을 보고 갈라야 한다.

### 6-4. 값이 같아 공유된 심볼

컴파일러가 같은 값의 상수를 한 심볼로 합친다. 그래서 글꼴 크기 14 와 버튼 id 14 가
같은 심볼일 수 있고, 그냥 ×N 하면 id 가 깨진다. `scn_dims.py` 는 이때 **심볼
테이블 끝에 새 int 심볼을 붙이고** 좌표 쪽 참조만 그리로 돌린다. 인덱스가 뒤에
붙으므로 기존 참조가 밀리지 않고, 점프테이블은 flow 상대라 flow 가 통째로 밀려도
그대로 맞는다(§3). 새 참조 인덱스는 기존 **런타임 슬롯 수** 뒤에 붙지만, 헤더
`[6:8]`에는 새로 붙인 **정의 수**만 더한다.

## 6-5. button.m02 배치 파이프라인

`config.scn` 처럼 좌표 배치가 자동 도출이 안 되던 화면을 풀기 위해 exe 의
button 명령 처리와 다원소 심볼 인덱싱을 추적했다.

```
op01 핸들러 0x408F27 : call [vtable+0x40]  = 객체별 명령 디스패처
button vtable 의 명령 핸들러 = 0x407A70    (메서드 점프테이블 0x407F34)
  m02 = 0x407B24
    - [esp+0x34] = argc. cmp 6/7/8/9 로 뒤쪽 인자를 조건부로 읽는다(가변 인자).
    - 인자 배열 [esi+0], [esi+4], … 를 순서대로 0x4089B0(심볼 해석)에 통과시켜
      위젯 생성 파이프라인에 넘긴다.
  0x406F90 : 위젯 노드 할당(0x40 바이트) 후 0x408020 에 인자 전달
  0x408020 : 노드 생성자 — 인자를 노드 필드에 저장
      node[0]=arg0  node[4]=arg1  node[8]=arg2  node[0xc]=arg3
      node[0x10]=arg4  node[0x38]=arg7
```

- `m02`는 arg0..4·arg7을 정수로 변환하고 arg5·6·8은 이미지 객체로 유지한 뒤,
  `0x406F90`이 역순 push하여 원래 순서 그대로 `0x408020`에 전달한다. 별도 인자
  재배치 오버로드는 없다: **arg0..3=x,y,w,h, arg4=id, arg5/6=off/on,
  arg7=mode, arg8=select**다.
- 과거 `config.scn`의 일부 호출이 `(string,string,int,…)`처럼 보인 원인은
  `02 00 06 06`을 “배열 심볼 하나”로 축약한 파서 버그였다. 실제로 이 정의는
  런타임 슬롯 6개라 이후 인덱스가 +5, 뒤의 `02 00 04 04`에서 다시 +3 된다.
  config는 헤더 정의 191개지만 런타임 슬롯은 199개(0..198)다.
- 슬롯을 펼치면 `config.scn`의 `button.m02` 41개가 모두 위 타입 시그니처와
  일치한다. `ujyu/scn_dims.py`는 좌표 59개와 공유 상수 10개를 안전하게 분리·확대한다.
  순차 파서가 scratch-object 메서드 직후 한 호출 경계를 놓치는 경우에는 객체 타입,
  알려진 메서드, 전 인자 심볼 타입을 모두 검증한 명시 호출만 보수적으로 합친다.
