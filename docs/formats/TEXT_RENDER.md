# 텍스트 렌더링 — 인코딩·폰트·글꼴 선택 (Studio Miris)

엔진이 **바이트를 문자로 쪼개고, 폰트를 골라, 화면에 그리는** 경로의 구조 명세.
한국어(CP949) 직접 렌더와 **가변폭 글꼴** 사용에 필요한 요소를 전부 담는다.
주소 찾는 법·절차는 [SKILL.md](../../SKILL.md) 2·6~10절, 도구는
[ujyu font](../../ujyu font)·`patch_exe.py`·`patch_fontrestore.py`.
검증 타이틀: 神無ノ鳥(2002) — 실측 주소는 그 exe 기준(파일오프셋 = VA − `0x400000`).

---

## 1. 문자 분할 = 리드바이트 비트맵

문자 추출 함수(神無ノ鳥 `0x438D50`)가 **256비트(32바이트) 비트맵**으로 "이 바이트가
2바이트 문자의 리드인가"를 판정한다.

```asm
mov edx, 0x80
and ecx, 7
sar edx, cl                      ; 마스크 = 0x80 >> (byte & 7)
shr ecx, 3                       ; byte / 8
mov cl, byte ptr [ecx+0x477468]  ; ← 리드바이트 비트맵 (32B)
test cl, dl
je  <1바이트 처리>
```

| | 값 (32B) | 리드로 인정되는 범위 |
|---|---|---|
| 원본 | `00×16 7F FF FF FF 00×8 FF FF 00 00` | `0x81–0x9F`, `0xE0–0xEF` (SJIS) |
| 패치 | `00×16 7F FF FF FF FF FF FF FF FF FF FF FF FF FF FF FE` | **`0x81–0xFE`** (CP949 전 범위) |

CP949 한글 리드(`0xB0–C8`)가 원본 비트맵에 없어서 **1바이트씩 쪼개지는 것**이 한글이
깨지던 유일한 원인이다. 증상은 폰트에 따라 달라 보인다 — 원본 SJIS 폰트에서는 반각
가나(`｡ｱｳﾀｻ…`), 한글 폰트에서는 `?`. 비트맵을 CP949 전 범위로 바꾸면 정상 렌더되고,
SJIS 리드도 새 범위에 포함되므로 **원문 일본어도 그대로 동작**한다.

> 이 테이블은 256바이트 룩업이 아니라 **32바이트 비트맵**이다. 256B 테이블만 찾으면
> 못 찾는다. 찾는 법: 문자열 그리기 루프에서 "다음 문자 추출" 호출을 따라가 `[base+idx]`
> 형태의 비트 테스트를 찾는다 (SKILL 6-1).

**메시지 리더는 무죄**: 리더(`0x408E00`)는 `≥0x80`이면 무조건 2바이트로 조립한다
(SJIS 판정 없음). 분할은 위 추출 함수에서만 일어난다.

**추출 함수의 모드 2**는 비트맵 대신 `cmp eax,0x80; jb` 를 써서 원래부터 CP949 호환이다.
본문 렌더는 비트맵 경로를 탄다.

## 2. 표시 텍스트 바이트 제약

메시지 리더가 바이트 값으로 분기하므로([VNEG.md](VNEG.md) §4) **화면에 나오는 텍스트의
모든 바이트는 `0x80` 이상**이어야 한다.

- ASCII 공백(`0x20`)에서 텍스트가 끊기고, ASCII 영숫자(`0x41`/`0x31`)는 표시되지 않는다.
- → 번역문의 ASCII는 **전각으로 정규화**(전각 ASCII = CP949 `A3xx`, 전각 공백
  `U+3000` = `A1A1`). `inject_text.py` 가 자동 처리한다.
- 원문의 제어코드(대사 끝 `%`=0x25 등)는 **원본 바이트 그대로 보존**한다.

## 3. 렌더 경로 — GGO_GRAY8 / TextOutA

LOGFONT 빌더(`0x4381D0`)가 두 vtable 중 하나를 고른다:

| vtable | 실제 렌더 | 비고 |
|---|---|---|
| `0x46F348` | **`GetGlyphOutlineA(GGO_GRAY8)`** (MAT2 = `0x477440`, 항등) | 본문 경로, AA |
| `0x46F360` | `TextOutA` | |

선택은 `arg3 & 0x100` 과 전역 `0x49B724`(EnumFont 콜백 `0x438C00` 이 폰트 피치를 보고
설정)로 결정된다.

**글자 폭은 vtable 과 무관하다** — 문자열 그리기 루프가 글리프 advance 를 그대로 쓴다:

```asm
0042D80A  call 0x4383A0    ; 글자 그리고 그 폭을 EAX 로 반환
0042D80F  add edi, eax     ; ← 폰트 advance 가 곧 자간
```

즉 **비례(가변폭) 렌더는 exe 패치가 아니라 폰트로 만든다**. 고정폭 폰트를 넣으면
고정폭으로, 비례 폰트를 넣으면 비례로 나온다. GGO 경로는 **글리프 아웃라인 좌표와
MAT2만** 쓰므로 OS/2·hhea 메트릭(winAscent 등)은 렌더에 영향을 주지 않는다.

## 4. 폰트 가공 ([ujyu font](../../ujyu font))

임의의 한글 폰트를 게임용으로 변환한다. 네 가지를 손본다.

### 4-1. 세로 시프트 (하단 잘림 보정) — 필수
GGO 경로가 글리프를 `gmptGlyphOrigin.y`(글리프 yMax) 기준으로 배치해 디센더가 셀
아래로 잘린다. **아웃라인 자체를 위로 이동**해야 한다 (메트릭 수정은 무효).
빌더가 표본 음절(`가 힣 그 장 렵`)의 최저점을 재서 `FONT_TARGET_BOTTOM_EM`(config)에
맞는 이동량을 자동 계산한다.

| 폰트 | 원래 한글 최저점 | 시프트 |
|---|---|---|
| Malgun Gothic (2048 upm) | −192 | **+256** (0.125 em) |
| Noto Sans KR (1000 upm) | −77 | **+108** (0.108 em) |
| IBM Plex Sans KR (1000 upm) | −159 | **+190** (0.190 em) |

#### 세로 맞춤 — 전역 시프트만으로는 모자란다

전역 시프트는 **한글 표본만** 보고 정한다. 그래서 한글보다 더 내려앉는 글자는
그대로 잘린 채 남는다. **디센더 깊이는 폰트마다 다르므로 한쪽에 맞춘 값이 다른
쪽에서 깨진다** — 실측:

| 폰트 | `( ) （ ） , / \ { } [ ]` 의 시프트 후 yMin | 40px 기준 |
|---|---:|---|
| IBM Plex Sans KR | +31 ~ +57 | 안 잘림 |
| **Noto Sans KR** | **−62 ~ −88** | **아래 4px 잘림** |

칸나기에서는 마음속 대사를 닫는 `）` 가 본문에 6,571 번 나와 바로 눈에 띄었다.

그래서 빌더가 시프트·일본어 병합을 끝낸 뒤 **모든 글리프를 셀 `0..1 em` 안으로
밀어 넣는다**(`build_font.fit_vertical`, 기본 창 `FIT_WINDOW_EM = (0.01, 0.99)`).

- 올려서 위가 넘치면 **세로로만** 누른다. 가로를 건드리면 advance 와 `hmtx` lsb
  (`= xMin`)를 다시 잡아야 하는데, **자간이 곧 advance 라**(§3) 글자 폭이 흔들린다.
  괄호 기준 압축률 0.966 이라 눈으로는 구별되지 않는다.
- 합성 글리프(`”` 등)는 좌표를 직접 못 만지므로 윤곽으로 풀어서 고친다.
- 폰트마다 값을 손으로 다르게 줄 필요가 없다 — **잘릴 글리프를 재서 각자 고친다.**

### 4-2. 전각 공백 폭
CP949 에는 `0x80` 이상인 좁은 공백이 없어 낱말 사이가 전각 공백(`A1A1`)이다.
`U+3000` 의 advance 를 **한글 폭의 절반**으로 줄여 자간을 자연스럽게 만든다.

### 4-3. 전각 ASCII 재매핑
`U+FF01~FF5E` 94자를 **비례 ASCII 글리프**로 연결한다. 바이트는 CP949 `A3xx` 그대로라
엔진 파싱에는 영향이 없고 화면만 자연스러워진다(§2 의 전각 정규화와 짝).

### 4-4. CFF(OpenType) → glyf(TrueType) 변환
글꼴 목록 콜백이 OpenType 을 걸러내므로(§5-1) CFF 소스는 TrueType 아웃라인으로 바꾼다
(cu2qu 로 3차→2차 베지어, `CFF `/`VORG`/`DSIG` 제거, `maxp` 1.0 + long `loca`).

> ⚠️ `sfntVersion` 을 `00010000` 으로 바꿔야 한다. `OTTO` 로 남으면 내용은 glyf 인데
> 헤더는 CFF 라고 선언하는 꼴이라 **Windows 가 설치를 거부**한다.

그 밖에: name 레코드를 face 이름으로 교체(엔진이 `CreateFontIndirectA(face)` 로 찾는다),
`OS/2.ulCodePageRange1` bit19(949) ON — HANGUL_CHARSET 요청에 매칭되도록.

## 5. 글꼴 선택 UI

### 5-1. 목록 필터 — 가변폭 폰트를 허용하려면
원작 콜백(`0x40C8A0`)은 고정폭·비비례 폰트만 목록에 넣어 한글 가변폭 폰트가 전부
탈락한다. `strstr` 헬퍼가 **매치되면 제외**하는 구조다:

```asm
test al, 4        ; TRUETYPE_FONTTYPE 만          (OpenType 탈락 → §4-4)
jne skip          ; strstr(name,"@")   세로쓰기
jne skip          ; strstr(name,"$")
jne skip          ; strstr(name,"P")   비례
jne skip          ; strstr(name,"Ｐ")  ＭＳ Ｐゴシック 류
jne skip          ; lfPitchAndFamily & 1 == 1  = FIXED_PITCH 강제
jne skip          ; lfOutPrecision & 3 == 3    = 아웃라인
```

| 패치 | 효과 |
|---|---|
| 비례 필터 2곳(`Ｐ`·FIXED_PITCH) → NOP | **가변폭 폰트 허용** |
| `P` 필터의 `jne`→`je` + 패턴을 `"Kannagi"` 등으로 교체 | 제외→**포함** 필터: 우리 폰트만 목록에 |

패턴 문자열은 기존 `Ｐ`/`P` 자리(8바이트)를 재활용한다.

## 4-5. 미번역 일본어를 CP949 로 실어 나르기 (`ujyu jpmap`)

번역하지 않고 원문으로 남기는 대목(H씬 등)이 있으면, 리드 비트맵 패치 이후 그 조각은
CP949 로 해석돼 깨진다. `inject_text.transcode_jp` 가 SJIS→CP949 로 옮기는데, **CP949 에
없는 글자**는 옮길 자리가 없다. 실측(神無ノ鳥): 미번역 1,274종 중 **185종**이 그렇다
(한자 183 + `ー` + `々`). 가나는 KS X 1001 에 그대로 있어 문제없다(`AAxx`/`ABxx`).

해결은 CP949 안에서 **안 쓰는 자리를 빌리는 것**이다. 두 종류가 있다.

| 영역 | 자리 | Windows CP949 → 유니코드 |
|---|---:|---|
| 사용자 정의 `0xC9A1`~`0xC9FE` · `0xFEA1`~`0xFEFE` | 188 | `U+E000`~`U+E0BB` |
| **한자 `0xCAA1`~`0xFDFE` 중 안 쓰는 것** | 최대 4,888 | 그 한자 자신의 유니코드 |

한자 영역을 빌린다는 것은 **그 자리에 다른 글자의 글리프를 얹는다**는 뜻이다. 예를 들어
`霊`(CP949 에 없음)을 `佳`(CAA2)의 자리에 실으면, 주입기는 `CAA2` 를 넣고 폰트는
`佳` 자리에 `霊` 글리프를 그린다.

> ⚠️ **이미 쓰는 자리는 비켜 간다.** 아래 둘은 자기 자리를 그대로 써야 하므로 예약된다:
> 미번역 일본어가 쓰는 글자 중 CP949 에 있는 것, 그리고 번역문이 쓰는 글자.
> `jpmap.scan()` 이 그 집합을 만들고 `slots()` 가 거기서 뺀 자리만 내놓는다.

사용자 정의 영역만으로는 **번역 초기에 모자란다** — 번역률이 낮으면 원문 전체가 대상이라
칸나기 기준 341자가 필요했다(자리는 188). 한자 영역까지 쓰면 3,300자 남짓 확보된다.

본문 렌더가 `GetGlyphOutlineA` 라 GDI 가 2바이트 코드를 이 표대로 유니코드로 바꾼 뒤
폰트 cmap 을 찾는다. 즉 **폰트의 `U+E000..` 에 글리프를 넣고 바이트 `0xC9A1` 을 주입하면
그 글리프가 나온다**(실측 확인). 리드 비트맵이 이미 `0x81–0xFE` 전 범위라 `0xC9`·`0xFE`
둘 다 리드로 잡힌다(§1).

- `ujyu jpmap` 이 미번역 조각을 훑어 빈도순으로 자리를 배정하고
  `translation/jp_charmap.json` 에 적는다.
- `build_font.merge_jp` 와 `inject_text.transcode_jp` 가 **같은 표**를 본다.
  표를 다시 만들면 **폰트도 반드시 다시 빌드**해야 한다 — 어긋나면 글자가 바뀐다.
- 자리가 모자라면 `jpmap.build` 가 멈추고 몇 자 부족한지 알려 준다.
- **폰트를 번역보다 먼저 만든다.** 표는 미번역 글자로 만들어지므로 번역이
  진행되면 바뀐다. 번역 0% 일 때 한 번 만들어 두면 그 뒤로는 자리가 줄기만
  한다(BOOTSTRAP 첫머리).

### 폰트 쪽에서 손봐야 하는 것

일본어 폰트를 그대로 심으면 안 된다. Noto Sans 기준 한글은 advance 920 에 y 8..935,
일본어는 advance 1000 에 y −89..850 다 — 한자가 크고 아래로 내려앉는다.

1. **균일 축소** `advance` 비율(920/1000)로 — 한글과 같은 칸을 쓴다. 게임의 문자열
   루프가 글리프 advance 를 그대로 자간으로 쓰므로(§3), 축소하지 않으면 일본어 줄만
   글자마다 80 씩 더 벌어진다. 한 줄에 두 문자가 섞이지 않는 타이틀이면 `JP_SCALE=1.0`
   으로 글자 크기를 우선해도 된다.
2. **세로 이동** 상자 중앙을 한글에 맞춘다 — 베이스라인 관습 차이를 흡수
3. **가나·한자 전체와 `々`·`、`·`。` 는 한글 폰트에 있어도 덮어쓴다**
   (`JP_OVERRIDE`, 엔진 기본값). Noto·본고딕 계열 한글 폰트는 CJK 한자를 다 갖고
   있지만 **한국식 자형**이라 일본어 문장에 섞이면 획이 다르게 보인다(`直`·`骨`·`海`).
   온점·반점은 자형이 아니라 위치 문제다 — 한글 폰트는 칸 가운데에 놓지만 일본어
   조판은 왼쪽 아래에 붙인다. 번역문은 주입 때 `．，` 로 바뀌므로 안전하다.

> ⚠️ `vmtx`/`vhea`(세로쓰기 메트릭)를 **지워야** 한다. OTF 뿐 아니라 Noto 같은 glyf
> 소스도 갖고 있다. 글리프를 추가할 때
> 같이 갱신하지 않으면 저장이 `KeyError` 로 죽는다. `vmtx` 는 `hmtx` 와 같은 클래스라
> 에러가 `hmtx` 이름으로 떠서 역추적이 헷갈린다.

> ⚠️ 새 글리프를 만들고 cmap 만 돌리면, 저장할 때 `post` 가 코드포인트에서 이름을 다시
> 만들어 내며 옛 글리프와 겹쳐 **옛것이 살아남는다**. 이미 있는 코드포인트를 덮어쓸 때는
> **그 글리프를 제자리에서 교체**할 것.

> ⚠️ `hmtx` 의 **lsb 를 글리프 xMin 과 맞춰야 한다.** 0 으로 두면 렌더러가 아웃라인을
> 그만큼 왼쪽으로 당겨 붙여, 좌여백이 큰 글자(`く` 204, `、` 52)가 칸 왼쪽에 쏠리고
> 오른쪽에 빈 자리가 남는다 — 화면에서 **자간이 제멋대로**로 보인다. advance 가 전부
> 같아도 그렇게 되므로 자간 문제로 오해하기 쉽다.

### 5-2. 열거 charset
글꼴 열거의 `lfCharSet` 을 `0x80`(SHIFTJIS) → `0x81`(HANGUL) 로 바꾸지 않으면 한국어
폰트가 열거되지 않는다. charset 설정은 exe 전체에 **2곳뿐** — 열거용(`0x40CBD1`)과
본문용(`0x438244`), 둘 다 패치한다.

### 5-3. face 선택 분기
빌더에 `arg3 & 0xff` 로 3갈래가 있다: 1/2 = 호출자가 준 이름(글꼴 창 선택),
그 외 = 하드코딩 이름(`0x477458`). 이 분기를 NOP 으로 눌러 case C 를 강제하면 **글꼴 창
선택이 무시**되므로 두지 말고, 기본 글꼴은 §6 으로 해결한다.

## 6. 기본 글꼴 = .data 의 16바이트 슬롯

시작 시 설정 변수에 exe 문자열을 기본값으로 등록한다 — MINCHO(`0x4756A0`, **본문이 쓰는
쪽**)와 GOTHIC(`0x475690`), 각각 `.data` 의 16바이트 슬롯. 한국어 Windows 에는
`ＭＳ 明朝` 가 없어 GDI 가 굴림으로 대체하던 것이 기본 글꼴이 굴림이던 이유다.
이 슬롯을 우리 face 이름으로 덮으면 기본 글꼴이 바뀐다.

> `common.csv` 의 `font_face`/`MINCHO`/`GOTHIC` 값은 **실측상 반영되지 않는다.**
> 기본 글꼴은 반드시 이 exe 슬롯으로 잡는다.

## 7. 글꼴 저장/복원 (코드 케이브)

**원작은 글꼴을 저장만 하고 다시 읽지 않는다.** 창에서 고른 글꼴이 세이브 파일에
기록되지만 재시작 시 `CreateFontIndirectA` 까지 도달하지 않아 매번 기본값으로 돌아간다.

해결: `.text` 끝 패딩에 코드 케이브를 얹어 **시작 시 세이브에서 읽어 §6 슬롯에 덮어쓴다**
(엔트리포인트 → 케이브 → 원래 OEP). `ujyu exe fontrestore`.

`systemdata.dat` 의 `+0x08` 이 글꼴 face 이름(널 종단)이다.
파일 전체 구조는 [SAVE.md](SAVE.md) §4.

안전장치 3중 — 파일 없음 / 읽은 바이트 부족 / 이름 첫 글자가 `0x20` 미만이면 아무것도
건드리지 않고 기본값을 유지한다.

## 8. 한국어 렌더 패치 묶음 — 요약

| 대상 | 내용 | 절 |
|---|---|---|
| 리드바이트 비트맵 (32B) | `0x81–0xFE` 로 교체 — **한글 렌더의 핵심** | §1 |
| 본문 charset | `0x80` → `0x81`(HANGUL) | §5-2 |
| 열거 charset | `0x80` → `0x81` | §5-2 |
| 목록 비례 필터 2곳 | NOP — 가변폭 허용 | §5-1 |
| 목록 `P` 필터 + 패턴 | 제외→포함, 우리 폰트만 노출 | §5-1 |
| GOTHIC / MINCHO 기본 슬롯 | 우리 face 이름 | §6 |
| case C 폴백 face | 우리 face 이름 | §5-3 |
| 코드 케이브 + OEP | 글꼴 저장/복원 | §7 |
| 폰트 파일 | 시프트·전각공백·전각ASCII·(CFF→glyf) | §4 |

오프셋은 타이틀마다 다르다 — config 에 채우고(`OFF_LEAD_BITMAP`·`OFF_CHARSET_*`·
`OFF_FILTER_*`·`OFF_FONT_*`·`CAVE_VA` 등) `ujyu exe` 가 한 번에 적용한다.

## 9. 배제된 가설 (재조사 방지)

| 가설 | 검증 결과 |
|---|---|
| CRT `_ismbblead`/`_mbctype`, `_setmbcp` | ❌ 게임이 CRT 코드페이지를 쓰지 않음 (`IsDBCSLeadByte` 임포트조차 없음) |
| 256바이트 리드 룩업 테이블 | ❌ 없음 — 32바이트 **비트맵**이다(§1) |
| 폰트 글리프/cmap 부족 | ❌ 폰트는 정상이었고 분할이 원인 |
| 메시지 리더의 SJIS 분할 | ❌ 리더는 `≥0x80` 을 무조건 2바이트 조립 |
| SJIS 리드 판정 idiom(`xor 0x20; sub 0xA1; cmp 0x3C`) 확장 | ❌ 본문 렌더는 이 경로를 타지 않음 (메뉴/세이브명 검증용). 패치해도 무해하나 불필요 |
| OS/2·hhea 메트릭으로 하단 잘림 보정 | ❌ GGO 는 메트릭 무시 — 아웃라인을 옮겨야 함(§4-1) |
| MAT2 세로 스케일 조정 | ❌ 위치 문제라 무효 |
| `common.csv` 의 `font_face`/`MINCHO`/`GOTHIC` | ❌ 반영되지 않음 — exe 슬롯이어야 함(§6) |
| 로케일 에뮬레이터로 글꼴 복원 | ❌ 원작이 애초에 안 읽음(§7) |
| 표시 텍스트에 반각 ASCII 사용 | ❌ `0x20` 에서 끊기고 영숫자는 미표시 — 전각 필수(§2) |
