# 해상도 — 엔진이 화면을 그리는 구조 (Studio Miris)

엔진이 해상도·배치·서피스 크기를 **어디서 읽어 어떻게 그리는지**의 구조 명세.
정수배(N×) 확대의 절차·찾는 법은 [SKILL.md](../../SKILL.md) 15절, 도구는
[ujyu scale](../../ujyu scale) (검증 타이틀: 神無ノ鳥 3×).

## 1. 렌더 파이프라인 = GDI 소프트웨어 컴포지터

DirectX·StretchBlt 없음. `CreateDIBSection` 백버퍼에 `BitBlt` 로 **1:1 합성**한다.

- **업스케일 경로가 없다** — 이미지는 네이티브 픽셀 크기 그대로 그려진다.
  화면을 키우려면 이미지 자체를 N× 로 교체해야 한다.
- 백버퍼는 창 크기를 따라간다.
- 렌더 자체는 해상도 독립 — 좌표·치수가 전부 **데이터에서** 온다(아래 2~4).

## 2. 화면 크기의 루트 = exe 즉치 상수

창(CreateWindowExA 클라이언트)·백버퍼 DIB·풀스크린 사각형을 만드는 코드에
원래 해상도(640=`0x280`, 480=`0x1E0`)가 **즉치(imm)** 로 박혀 있다. exe 가 전역으로
고정하는 것은 **이것뿐**이다 — 개별 아이템의 배치·서피스 치수는 exe 에 없다(§3·4).

- 神無ノ鳥 실측: 폭 4곳(`0x764e/0xb879/0xcdb6/0x110a0`) + 높이 4곳, 총 9바이트 패치로
  화면 N×. 640×480 크기의 버퍼 상수도 없다(버퍼는 `w*h*bpp` 동적 할당).
- 3× 급에서는 메모리 사용이 커져 PE `LARGEADDRESSAWARE` 를 함께 켠다.

## 3. 레이아웃 계층 1 — `common.csv` (아카이브별!)

배경·캐릭터 같은 **월드 레이어**와 텍스트 UI 의 배치는 설정 파일이 정한다
([COMMON_CSV.md](COMMON_CSV.md)):

- `layer,<이름>,x,y,w,h,…` — 월드 레이어. 서피스는 이미지 크기에 자동으로 맞으므로
  이미지 N× + 레이어 좌표/치수 ×N 이면 끝. `.scn` 에는 이들 치수가 없다.
- `textwindow*`(위치·크기·여백), `int,text_size`/`text_line_height`/`select_*` —
  텍스트·선택지 배치.
- ⚠️ common.csv 는 **시나리오 아카이브마다 내용이 다르다**(고유 변수 정의 포함).
  반드시 각 아카이브의 자기 것을 **제자리 편집**한다 — 통째 주입하면 변수 테이블이
  밀려 미초기화 참조 크래시([COMMON_CSV.md](COMMON_CSV.md) 참조).

## 4. 레이아웃 계층 2 — `.scn` 명령층의 치수

로고·타이틀·메뉴·CG 뷰어처럼 **명시적 치수로 그리는 화면**은 그 x,y,w,h 가
`.scn` 안에 있다 ([VNEG.md](VNEG.md) 구조 기준):

- **구조화 명령/심볼 정의** `<op> <slots:u16 BE> <argc>`의 int
  인자(`01`+int32 BE). op는 객체 타입 id — `07`=layer,
  `08`=textwindow, `0c`=button, `16`=scroll 정의의 앞 인자들이
  x,y,w,h다. (예: title.scn 버튼 폭 `INT 153`.) `slots`가 2 이상이면
  정의 하나가 여러 연속 런타임 심볼 인덱스를 차지한다.
- **명령 영역의 2바이트 BE 즉치** — int32 인자 형태가 아니라 워드로도 박힌다.
  예: mlogo.scn 은 이미지마다 `01 40 00 f0 01 18 00 f0` = (320,240,280,240).
- 이 치수가 곧 **서피스 크기**다. 이미지를 N× 했는데 씬 치수가 1× 면 PNG 로더가
  이미지를 서피스 폭으로 clamp 하고, 이후 픽셀 복사에서 힙이 깨져 크래시한다
  (SKILL 15-4; clamp 분기를 없애는 패치는 금지 — 리사이즈가 안전하지 않다).
- 치수 편집은 **길이 불변**(값만 교체)이라 flow 가 안 밀린다 — 점프테이블
  재매핑([VNEG.md](VNEG.md) §3)이 필요 없다.
- 주의: 명령 영역에는 좌표 외에 인덱스·색상·타이밍 정수가 섞여 있다.
  `ujyu/scn_dims.py`는 검증된 객체 타입·메서드 시그니처만 바꾼다.
  `config.scn`도 다원소 심볼 슬롯과 `button.m02` 시그니처를 확인해 자동 스케일
  대상으로 전환했다.

### 4-1. 애니메이션 — 좌표만 키우고 **시간은 그대로 둔다**

움직이는 화면(스태프롤·슬라이드인)은 목표 좌표와 소요 시간을 한 호출에 같이 넘긴다.
시간까지 ×N 하면 배속이 절반이 되고, 롤은 노래에 맞춰 있어 어긋난다. 반대로 좌표만
키우면 **이동 거리와 창이 같이 커져 보이는 속도는 그대로**다.

| 호출 | 인자 | ×N 대상 |
|---|---|---|
| `layer.m05(x, y, ms)` | 그 좌표로 이동 | `x, y` |
| `textwindow.m20(y)` | 스크롤 위치 즉시 설정 | `y` |
| `textwindow.m40(y, ms)` | 그 위치까지 스크롤 | `y` |

**음수 좌표가 있다.** 화면 밖에서 들어오는 연출이라 그렇다 — 神無ノ鳥 스태프롤은
가림막이 `y=-60`(위쪽 화면 밖)에서 내려오고, 롤 본문은 `y=-360`에서 스크롤을 시작해
`y=4120`까지 100초간 흐른다. 좌표 자리의 0 이하 값을 통째로 버리면 이것들이 1× 로
남아 시작 프레임에 띠가 보이고 롤이 중간부터 뜬다. **버릴 것은 `0`(×N 해도 0)과
`-1`(자동 센티널)뿐**이다. 쓸 때도 int32 는 부호 있는 값이라 signed 로 넣어야 한다.

## 5. 이미지 (cg 아카이브)

- **콘텐츠**(배경·캐릭터·이벤트 CG): N× 로 교체. 서피스는 따라온다(§3).
  - ⚠ 콘텐츠 이미지를 1× 로 남겨두면 **서피스만 N× 라 화면의 1/N² 만 덮는다**.
    神無ノ鳥 실측: 미리스 로고 뒤 흰 배경 `bg00b.png` 를 1× 로 두어 좌상단
    1/4 만 흰색이었다. ×N 하니 해결(크래시 없음). `CG_FORCE_1X` 는 정말로
    치수가 고정된 것만 넣고, 넣었으면 실제 화면을 확인할 것.
- **UI**(대사창·프레임·커서·메뉴·얼굴): 1× 유지 + 배치만 이동(큰 아트 + 작은 UI,
  SKILL 15-6)하는 구성이 안전하다. 실수로 N× 하면 §4 의 clamp 크래시.
- **공유 이미지 주의**: 한 엔트리가 여러 화면에서 쓰이면 크기는 하나뿐 — 한쪽을 N×
  하면 다른 쪽 서피스와 어긋난다.

### 5-1. AI 업스케일러로 키우기 (선택)

원작 아트는 저해상도라 단순 리샘플(bilinear)이면 흐릿하다. Topaz Photo AI·waifu2x 같은
외부 업스케일러를 쓰면 훨씬 낫다. 절차:

```bash
python engine/ujyu/scale.py cg-export <원본 cg.axr> --out <작업폴더>   # 1) 대상만 추출
#   → <작업폴더>/art/   배경·캐릭터 스프라이트 (AI 업스케일 권장)
#   → <작업폴더>/small/ 섬네일·버튼·로고 (리샘플로 충분)
#   → _manifest.tsv     파일별 원본/목표 치수
# 2) art/ 를 업스케일러에 넣어 ×N. 결과는 **같은 파일명**으로 저장.
python engine/ujyu/scale.py cg <원본 cg.axr> --out <출력 cg.axr> --from-dir <결과폴더>
```

- `--from-dir` 은 하위 폴더까지 재귀로 파일명을 찾고, **없는 파일은 bilinear 폴백**
  후 경고한다(전부 업스케일할 필요 없음).
- 업스케일 결과 치수가 정확히 원본×N 이 아니면 **그 자리에서 LANCZOS 로 보정**한다.
  서피스 치수(§4)와 1픽셀이라도 어긋나면 클램프 크래시라 이 보정은 필수다.
- **투명도 주의**: 캐릭터 스프라이트는 알파가 있다. 알파를 지우거나 배경을 합성하는
  업스케일러 설정은 피한다(모드가 달라지면 도구가 원본 모드로 되돌린다).
- 텍스트가 그려진 이미지(로고·버튼)는 AI 업스케일이 글자를 뭉갤 수 있다 — 그런 것은
  번역·재렌더 대상(SKILL 14절)이거나 `small/` 로 두는 편이 낫다.

## 6. 무비 (.dmj) — 네이티브 HD 재생 가능 ✅

무비가 제대로 나오려면 두 가지가 맞아야 한다: **확대 배율**(§6-1)과 **프레임 버퍼
크기**(§6-2). 둘 다 규명·해결됐고 1280×960 네이티브 재생을 실제로 확인했다(§6-3).

### 6-1. 엔진은 무비를 2배로 확대해 그린다 — 끌 수 있다 ✅

무비 객체 ctor 가 블리터에 **스케일 플래그 `2`** 를 넘긴다. 원작의 320×240 무비가
640×480 화면을 채우는 이유다. 이 즉치를 `0` 으로 바꾸면 **1:1** 로 그려진다.

```
神無ノ鳥 ctor 0x458E10 안:
  0x458EE7   6a 02   push 2    <- 2배 확대 (원작)
             6a 00   push 0    <- 1:1 (네이티브)
  플래그는 블리터 셋업 0x45B7F0 의 1번 비트로 들어간다
  (and esi,2 -> [obj+0x43c] = 8 또는 16, 블리트 루틴 테이블도 갈린다)
```

도구: [ujyu exe movie](../../ujyu exe movie) — `config.MOVIE_NATIVE` /
`config.OFF_MOVIE_SCALE`.

| 화면 | `.dmj` 치수 | 확대 플래그 | 결과 |
|---|---|---|---|
| 640×480 (1×) | 320×240 | 2 (원작) | 화면을 채움 ✅ |
| 1280×960 (2×) | 640×480 | 2 | 화면을 채움 ✅ (2배 확대라 부드러움) |
| 1280×960 (2×) | 1280×960 | 2 | **크래시** ❌ (2560×1920 을 그리려다 넘침) |
| 1280×960 (2×) | 1280×960 | **0** | **네이티브 HD 재생** ✅ |

확대를 끄면 **무비 치수 = 화면 치수**여야 한다. 절반짜리 무비를 그대로 두면
좌상단에 작게 나온다.

### 6-2. 프레임 버퍼 크기는 헤더 `+0x14` 가 정한다 ✅

DMJ0 헤더 오프셋 `+0x14` 의 u32 = **최대 프레임 페이로드 크기**다. 디코더 ctor 가
이 값을 더해 버퍼를 잡는다:

```
0x45B710:  픽셀 = ((w+7)&~7) * ((h+7)&~7)
           alloc( w*8 + (픽셀*3 + 0x2052C)*4 + [헤더+0x14] )
```

원작 `opening.dmj` 는 이 필드가 `0xE77F` = 59,263 이고 **실제 최대 프레임과 정확히
일치**한다. 재인코딩할 때 원본 헤더를 그대로 복사하면 이 값이 남아, 그보다 큰
프레임부터 버퍼를 넘겨 **화면이 깨진다**(크래시는 아니다).

| 무비 | 평균 | 최대 | 헤더 `+0x14` | 결과 |
|---|---:|---:|---:|---|
| 원작 320×240 | 18.1KB | 57.9KB | 59,263 | 정상 |
| 640×480, 상한 없음 | 94.4KB | 191.3KB | 59,263 (거짓) | **3.6초부터 깨짐** ❌ |
| 640×480, `--max-frame 57000` | 48.0KB | 55.7KB | 59,263 | 전편 정상 ✅ |
| 1280×960 | 158KB | 267KB | 59,263 (거짓) | **전면 노이즈** ❌ |
| 1280×960 | 158KB | 267KB | **273,447 (실측)** | **전편 정상** ✅ |

→ `dmj_encode.py` 는 이제 인코딩이 끝난 뒤 **실측 최대값을 `+0x14` 에 기록**한다.
해상도와 무관하게 안전하므로 `--max-frame` 은 용량을 묶고 싶을 때만 쓰면 된다.
예전에 "~64KB 프레임 한계" 로 적었던 것은 이 필드를 몰라 생긴 오해였다.

(본 인코더는 전 블록 intra 라 원작의 인터프레임 델타보다 프레임이 크다 — 델타
인코딩을 구현하면 같은 화질에 훨씬 작아진다.)

> **화질을 올리는 방법**: 원본을 AI 업스케일한 소스를 목표 치수로 **다시 다운샘플**해
> 인코딩한다(`dmj_encode.py --size <치수>`). 디노이즈·디테일 이득이 있다.

### 6-3. 검증 (2026-07-28, 神無ノ鳥 1280×960 빌드)

게임을 직접 실행해 오프닝 씬을 자동진행(▶)으로 통과시켜 확인했다. 자동진행을 쓰는
이유는 클릭이 무비를 스킵해 버리기 때문이다.

- `push 2` + 1280×960 무비 → 재생 시작 ~4초 만에 프로세스 사망(크래시 재현)
- `push 0` + 헤더 `+0x14` 미수정 → 크래시는 없으나 화면 전체가 노이즈
- `push 0` + 헤더 `+0x14` 수정 → 타이틀 로고·크레딧까지 **깨짐 없이 전편 재생**
  후 다음 씬으로 정상 진행

재생 경로: 재생 `0x40d710`(op `0x27`) → 무비 ctor `0x458e10` → 디코더 ctor
`0x45b710` → 블리터 셋업 `0x45b7f0` → 프레임 루프 `0x459040` → 프레젠트
`[edx+8]` @`0x459073`. 무비 색 R↔B 스왑은 `miris.dmj` 에서 수정 완료(컴포넌트 순
B,G,R). 오디오 `*.adp`("ADPx" 커스텀 ADPCM)는 미해독이라 원본을 그대로 쓴다.

## 7. 정수배(N×) 확대 시 손댈 것 — 요약

| 대상 | 처리 |
|---|---|
| exe 화면 상수 (§2) | 폭·높이 즉치 ×N (+ LARGEADDRESSAWARE) |
| common.csv (§3) | 각 아카이브 **자기 것 제자리**: layer·textwindow·text_size 등 ×N |
| .scn 명령층 치수 (§4) | 명시 치수 화면(title/mlogo/cg…)의 x,y,w,h ×N (int32·2바이트 BE 양쪽) |
| cg 이미지 (§5) | 콘텐츠 ×N, UI·얼굴 1× + 위치 이동 |
| 무비 (§6) | 미해결 — 네이티브 크기로 나옴 |

도구: [`ujyu scale`](../../ujyu scale) (`common`/`dims`/`cg`/`exe`) — 타이틀
`config.py` 의 `SCALE`·오프셋·분류 설정으로 구동되고, `build_patch.py` 가 `SCALE>1` 이면
각 단계에 포함해 빌드한다. 검증: 神無ノ鳥 3× 배포 산출물과 전 파일 바이트 동일 재현.
