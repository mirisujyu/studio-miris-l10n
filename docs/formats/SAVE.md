# 세이브 데이터 포맷 (`save/*.dat`)

Studio Miris 엔진의 세이브·설정 파일 구조. 파일 경로는 exe 가 아니라 **`common.csv`
의 `file,<키>,<경로>` 정의**에서 온다([COMMON_CSV.md](COMMON_CSV.md)) — exe 에는
`savedata` 같은 문자열이 아예 없다.

```
file,systemdata,save/systemdata.dat
file,readdata,save/readdata.dat
file,savedata0,save/savedata0.dat     ← 슬롯 0
…
file,savedata19,save/savedata19.dat   ← 슬롯 19 (총 20슬롯)
file,commondata,save/commondata.dat
```

| 파일 | 크기(실측) | 내용 |
|---|---:|---|
| `savedataN.dat` | 300~400B | 슬롯별 세이브 (§1) |
| `systemdata.dat` | 56~61B | 글꼴·화면 설정 (§4) |
| `readdata.dat` | 273~330B | 기읽음(既読) 플래그 (§6) |
| `commondata.dat` | 20B | 전역 공통 데이터 (§5) |

정수는 전부 **big-endian**이다.

## 1. `savedataN.dat`

암호화·압축 없는 **순차 직렬화**다. 절대 오프셋 테이블이 없어 앞쪽 문자열 길이가
바뀌면 뒤가 통째로 밀린다(길이를 바꿀 때 주의).

### 1-1. 선두 문자열 3개 (널 종단)

| # | 내용 | 인코딩 | 예 |
|---|---|---|---|
| 0 | **세이브 제목** — 로드 화면에 뜨는 이름. 보통 그 시점의 씬 제목 | 본문과 동일(한국어판=CP949) | `오프닝` / `칸나기산에　사는　새` |
| 1 | 성(姓) — `common.csv` 의 `string,LN` 기본값 | SJIS/CP949 | `デフォルト名字` |
| 2 | 이름 — `string,FN` 기본값 | 〃 | `デフォルト名前` |

> 제목이 CP949 로 저장되는 것은 인게임 텍스트와 같은 경로이기 때문이다. 즉 번역본에서
> 만든 세이브는 원문판에서 깨진다(그 반대도 마찬가지).

### 1-2. 씬 참조 레코드

문자열 뒤로 아래 레코드가 여러 번 나온다 (실측 5~8개 — 실행 중인 스레드/스택 추정):

```
<u8 플래그> 10 <u8 인덱스> <u32 토큰> <씬이름 cstr>
```

- `10` 은 VNEG 심볼 참조 마커와 같은 값이고, 그 뒤 1바이트가 인덱스다([VNEG.md](VNEG.md) §2).
- **`u32 토큰` = 그 씬 `.scn` 내용의 CRC32 (big-endian)** ✅ 실측 확인.
  세이브를 만든 시점의 시나리오 데이터를 식별하는 값이라, 번역·리팩으로 `.scn` 이
  바뀌면 어긋난다(→ §2).
  검증: 2× 빌드에서 만든 세이브 토큰 `f6 23 dd 2a` = `crc32(0506_01.scn)` 의 BE 표기.
- **토큰은 레코드마다 다르다** — 각 레코드는 **자기가 참조하는 씬**의 CRC 를 갖는다.
  (2026-07-30 정정. 이전 판에는 "한 세이브 안의 모든 레코드가 같은 값"이라고 적혀
  있었는데, 한 씬만 거친 세이브에서만 그렇게 보였던 것이다.)
  실측: `savedata10` 은 `0506_02`=`8a4ea88a` / `0506_01a`=`dd0a5d23`,
  `savedata11` 도 `0506_02` 와 `0506_02b` 가 서로 다르다. 분기를 지난 세이브에서
  분명히 드러난다. `ujyu save show` 가 레코드별로 일치(`=`)/불일치(`!`)를 표시한다.
- 씬 이름은 확장자 없는 `.scn` 이름(`0506_01`)이다.

**마지막 레코드 = 현재 진행 위치.** 앞의 레코드들은 토큰이 4바이트를 채우지만,
맨 끝 씬 참조만 형태가 다르다:

```
<u16 BE 진행위치> <u16 BE 인덱스> <씬이름 cstr> <u32 토큰>   ← 파일 끝
```

- **진행 위치**는 그 씬 안의 오프셋이다. 실측: 오프닝 세이브 14,390 / 선택지 직전
  세이브 17,080 — 둘 다 `0506_01.scn` 크기(20,113) 이내이고, 이야기 진행 순서와
  대소가 일치한다.
- **인덱스**는 라벨/스레드 번호로 보인다(값 2·5). ❓
- 아직 진입하지 않은 분기 씬은 **위치 0** 으로 기록된다(실측: `0506_01a` = `00 00 00 01`).
  → 씬 처음부터 시작시키려면 이 u16 을 `00 00` 으로 두면 된다.

### 1-3. 그 밖에 들어 있는 것 (실측 확인)

- **현재 표시 중이던 대사/나레이션 텍스트**와 **화자명**이 그대로 박혀 있다
  (예: `（…뭐라고　대답하지？）`, `이카루`). 로드 화면 미리보기용으로 보인다.
- 선택지를 지난 세이브에는 **분기 씬 이름**(`0506_01a`)이 별도 레코드로 들어 있다.
- 나머지 정수 필드(플래그·변수·좌표)는 미해독. ❓

## 2. 토큰 불일치 = 씬 앞부분부터 재개

`load.scn` 에 다음 메시지가 있다:

> セーブデータが参照するシナリオデータが更新されたため正常ロードできません。
> 該当シナリオの先頭部分から再開します。画面や音楽を消去するため、
> 画面表示が本来とは異なる場合があります。

즉 토큰이 안 맞아도 **로드는 되고, 해당 시나리오의 처음부터 재개**한다. 번역·리팩으로
아카이브를 다시 만들면 토큰이 어긋나므로 이 경로를 타게 된다 — 정상 동작이다.

## 3. 실용: 원하는 씬에서 시작하는 세이브 만들기

테스트할 씬으로 바로 들어가는 세이브를 손으로 만들 수 있다.

1. 게임에서 아무 데서나 한 번 세이브해 `savedataN.dat` 를 얻는다.
2. 그 파일의 **씬 이름 문자열만** 원하는 씬으로 바꾼다.
   **같은 길이로 바꾸면** 뒤쪽 오프셋이 밀리지 않아 가장 안전하다
   (`0506_01` → `0506_02` 처럼 자릿수가 같은 씬).
3. **진행 위치(§1-2 의 u16)를 0 으로** 두어 씬 처음부터 시작하게 한다.
4. 다른 슬롯 번호로 저장해 넣는다(기존 세이브 보존).

```python
import re
b = bytearray(open('savedata1.dat', 'rb').read())
b[:] = bytes(b).replace(b'0506_01\0', b'0506_02\0')          # 씬 이름 (동일 길이)
s = [m.start() for m in re.finditer(rb'0506_\d\d[a-z]*\0', bytes(b))][-1]
b[s-4:s-2] = b'\0\0'                                          # 진행 위치 -> 0
open('savedata2.dat', 'wb').write(bytes(b))
```

토큰은 안 맞겠지만 §2 대로 **그 씬 앞부분부터 재개**한다. 미리보기 텍스트·화자는
이전 씬 것이 남아 있어 로드 화면에만 어색하게 보이고, 진행에는 영향이 없다.

> 길이가 다른 씬으로 바꾸려면 문자열 길이 변화만큼 전체가 밀리는데, 형식이 순차
> 직렬화라 **원칙적으로는 그대로 동작해야** 한다(절대 오프셋 없음). 다만 미해독
> 필드가 남아 있으므로 같은 길이 치환을 우선한다.

## 4. `systemdata.dat` — 글꼴·화면 설정

56~61바이트. 크기가 다른 건 **글꼴 이름 길이** 때문이다.

| 오프셋 | 형 | 값(실측) | 뜻 |
|---|---|---|---|
| `+0x00` | u32 BE | `0x00000021` | 헤더/버전 (모든 설치본 동일) |
| `+0x04` | u32 BE | `0x00000001` | 〃 |
| `+0x08` | cstr | `KannagiKR-Noto` / `ＭＳ 明朝`(SJIS) | **글꼴 face 이름** |
| 이후 | 38B 고정 | — | 화면·소리 설정 (아래) |

글꼴 이름은 `TEXT_RENDER.md` §7 의 코드 케이브가 **시작 시 읽어 기본 글꼴 슬롯에
덮어쓰는** 값이다(원작은 저장만 하고 읽지 않는다).

### 4-1. 창 위치 — 파일 **끝에서** 세는 7바이트 ✅

글꼴 이름이 가변 길이라 앞에서 세면 어긋난다. 끝 기준이면 파일 크기와 무관하게 일정하다:

| 위치 | 형 | 뜻 |
|---|---|---|
| `[-7:-5]` | u16 BE | **창 x** |
| `[-5:-3]` | — | `00 00` |
| `[-3:-1]` | u16 BE | **창 y** |
| `[-1]` | u8 | `00` |

검증: 창을 **x 는 조금, y 는 크게** 옮기고 저장하니 `x 106 → 22`(Δ−84),
`y 194 → 1861`(Δ+1667) 로 변화 폭이 조작과 일치했다. 다른 설치본도 같은 규칙으로
읽힌다(원본 x=1659 y=1239 / 640판 x=1667 y=712).

### 4-2. 나머지 꼬리 (미확정)

```
000000ff 000000ff 000000b4 0101 000000ff 0001 0001 00000000 <A> ... <x> 0000 <y> 00
```

- `000000ff` ×2 — 색 지정(흰색)으로 보인다. ❓
- `<A>` = `[-12:-10]`, 관측 `0x03e8`(1000). 창 위치만 바꿔 저장했는데 `0` 이 되었다 —
  자동 모드 대기 시간(ms) 계열로 추정하나 왜 초기화됐는지는 미확인. ❓

## 5. `commondata.dat` — 전역 공통 데이터

20바이트 고정. 세이브 슬롯과 무관한 **전역 진행 상태**(엔딩 해금·갤러리 등)로 추정한다.

```
00 00 00 01 | 00 00 00 00 | 33 00 00 00 | 00 00 00 04 | 00 00 00 00
   버전=1        0          플래그?        4?              0
```

원본·번역본·2× 빌드 **세 설치본에서 완전히 동일**해 필드를 가를 단서가 없다. 진행에 따라
어느 바이트가 바뀌는지 확인하려면 엔딩을 본 뒤 diff 하는 것이 확실하다. ❓

## 6. `readdata.dat` — 기읽음 플래그

| 오프셋 | 형 | 값(실측) | 뜻 |
|---|---|---|---|
| `+0x00` | u32 BE | `0x44e` = 1102 | 엔트리 수로 추정 ❓ |
| `+0x04` | u8 | `01` | ❓ |
| 이후 | 비트/바이트 배열 | 대부분 `00` | 대사별 읽음 표시 |

파일 크기가 설치본마다 다르다(원본 273B, 번역본 330B). 선두 값 1102 는 같으므로
크기 차이는 뒤쪽 배열 길이에서 온다 — 진행하며 커지는 구조로 보인다. ❓

> 이 세 파일은 **번역·리팩과 무관**하다. 지워도 게임이 기본값으로 다시 만든다
> (글꼴 설정만 초기화된다).
